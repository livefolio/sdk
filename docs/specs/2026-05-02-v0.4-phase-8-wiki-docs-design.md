# v0.4 Phase 8 — User wiki, API reference, and agent skills

**Status:** Draft
**Date:** 2026-05-02
**Companion plan:** `docs/plans/2026-05-02-v0.4-phase-8-wiki-docs.md`
**Depends on:** Phase 7 (`docs/specs/2026-05-02-v0.4-phase-7-docs-refresh-design.md`) — landed. README + AGENTS.md sweep is done; this phase builds the comprehensive docs site on top.

## Goal

Phase 7 made the existing in-repo docs honest. Phase 8 builds the **user-facing documentation site**: comprehensive guides, mechanically-generated API reference, runnable code samples, and a small set of focused agent skills that help Claude (and other agents) author strategies and custom adapters against the SDK.

After this phase:

- A new TypeScript user lands on the docs site and can write a working strategy from "install" to "first backtest" without reading source.
- Every public symbol in `src/index.ts` has a generated reference page with parameters, return type, and a worked example.
- Every code sample on the site is a real `.ts` file in the repo, type-checked in CI, with no possibility of silent drift.
- An agent helping a user author a `TacticalSpec` or implement a custom `DataFeed`/`Executor`/`Calendar`/`FeatureCache` has a focused skill that loads the relevant patterns and validation checklist.

This is the docs-as-product phase — what an external adopter actually consumes.

## Non-goals

- **Multi-version docs** (v0.3 alongside v0.4). v0.3 is a regression target inside `parity/`, not a supported public API. Site is v0.4-only.
- **Search-engine optimization, marketing, branding.** Tooling defaults are fine.
- **Per-locale translation.** English only.
- **Hosted commenting/feedback widgets.** GitHub Issues is the feedback channel.
- **Re-litigating the four-layer architecture.** That's `2026-04-28-generalized-strategy-architecture-design.md`. The Architecture section of the docs site links to it.

## Tooling

**VitePress + TypeDoc.**

| Component | Choice | Why |
|---|---|---|
| Site framework | VitePress | Lightweight, Vite-native (familiar to TS devs), markdown-first, ships with search + dark mode. Single-config deploy. |
| API reference generator | TypeDoc | Mechanical reference from TSDoc comments — params, types, return values, declared examples. Refresh on every build, no manual upkeep. |
| Plugin glue | `vitepress-plugin-typedoc` | Renders TypeDoc output as native VitePress pages so reference and narrative live under one navigation tree. |
| Hosting | GitHub Pages via Actions | Already implicit in repo location; deploy is one workflow file. |
| Code-sample harness | `scripts/docs/*.ts` files referenced from markdown via `<<<` includes | Runnable in CI; markdown imports the literal file content so the rendered code block can never drift from the file. |

**Why not alternatives:**
- **TypeDoc alone** generates reference but no narrative — guides, recipes, architecture pages need a real site framework.
- **Astro Starlight** is the strongest competitor; switch would be cosmetic. VitePress wins on ecosystem familiarity and TypeDoc plugin maturity.
- **Docusaurus** is heavier (React, MDX, more dependencies) without payoff for this size of project.
- **Plain markdown in `docs/wiki/`** rendered by GitHub: no search, no nav, no API reference automation. Rejected.

## Code-sample harness — runnable, not illustrative

**Decision: every code sample is a real TS file.** Inline-only markdown samples can drift silently; the parity gate has already proven the value of "code that can't lie" for this project.

Structure:

```
scripts/docs/
  getting-started/
    install.ts             # not strictly runnable but imports must resolve
    first-strategy.ts      # full quick-start; print final snapshot
  guides-authoring/
    rule-trees-hysteresis.ts
    synthetics-leverage.ts
    rebalance-weekly.ts
    ...
  guides-runtime/
    custom-datafeed.ts
    custom-executor.ts
    custom-calendar.ts
    custom-feature-cache.ts
  guides-dialect/
    minimal-dialect.ts
  recipes/
    v3-replication.ts
    multi-asset-trend.ts
    mean-reversion.ts
    realistic-slippage.ts
```

Each file is `npx tsc --noEmit` clean. Files that perform a backtest run end-to-end; files that demonstrate a type or pattern only need to typecheck.

In markdown, samples are included via VitePress's snippet syntax:

```md
<<< @/../scripts/docs/getting-started/first-strategy.ts
```

This embeds the file's contents verbatim at render time. Drift becomes impossible because edits to the markdown are edits to the source file.

CI gate: a new `npm run docs:check` script type-checks every `scripts/docs/*.ts` file plus runs the ones marked `@runnable` in a TSDoc tag. Phase-8 acceptance includes this script being green.

## API reference — TSDoc audit

TypeDoc only generates as much detail as TSDoc comments declare. Today the SDK source has uneven TSDoc coverage (some functions documented, many not). Phase 8 includes a one-pass audit:

- Every exported symbol from `src/index.ts` gets a one-line summary.
- Every exported function additionally gets `@param` for each parameter, `@returns`, and at least one `@example` block.
- Interface contracts (`DataFeed`, `Executor`, `Calendar`, `FeatureCache`) get a class-level explanation of what the implementation contract requires (semantics, not just types — e.g., "DataFeed.bars must return bars in ascending t order; range.from is inclusive, range.to is exclusive").

This audit is *the* mechanism by which "comprehensive function documentation" gets delivered — the site renders what the source declares.

## Agent skills

Three focused skills, scoped narrowly. Skills earn their keep on **procedure**; reference belongs on the site.

| Skill | When it fires | What it loads |
|---|---|---|
| `livefolio-tactical-author` | Agent is writing or modifying a `TacticalSpec` (file imports from `@livefolio/sdk/tactical`, or user message mentions "tactical strategy" / "rebalance schedule" / "rule tree") | Dialect schema cheat sheet; common patterns (rebalance gate / hysteresis / synthetics); validation checklist (every `Comparison.id` unique within a spec, every `feature.id` referenced by a comparison is declared in `features`, every weight key in `op:'allocate'` is in `universe`, weights sum to 1, leverage falls within documented bounds, synthetic-asset `expense` is decimal not percent). Points at site for depth. |
| `livefolio-custom-adapter` | Agent is implementing a custom `DataFeed` / `Executor` / `Calendar` / `FeatureCache` (file declares `implements DataFeed` / etc., or user message mentions "custom data feed" / "broker adapter" / "exchange calendar") | Interface contract; semantics gotchas (TZ handling, range inclusivity, async behavior, error conventions); reference-impl source as starting point; "things to verify before shipping" checklist (returns sorted by t, idempotent, handles empty range, etc.). |
| `livefolio-debug-strategy` (conditional — write only if Tasks 10-11 reveal a recurring debugging pattern that's worth encoding) | Agent is investigating a strategy producing unexpected output | Troubleshooting checklist: SMA warmup window, missing feature values (and what `fromSpec` does when a feature is undefined), calendar mismatch (asset listed on wrong exchange), rebalance schedule miscount, hysteresis state carryover across runs. |

Skills live in `~/.claude/skills/livefolio/` (user's machine) for local development and in this repo under `.claude/skills/` for in-repo sharing. Phase 8 ships the in-repo copy; the user-machine install is documented in the site's "Setting up Claude with the SDK" page.

Each skill body is short (~50-100 lines). Skill files **must not** duplicate site content — they reference site URLs for explanation and reserve their own body for the procedural checklist that's awkward to express in narrative prose.

## Hosting and deploy

GitHub Pages via Actions. The workflow:

1. Trigger on push to `main` (after merge of phase 8) and on PRs (preview only).
2. Run `npm run docs:check` (type-check samples).
3. Run `npm run docs:build` (generate TypeDoc output → run VitePress build → emit static site).
4. Deploy `docs-site/.vitepress/dist/` to GitHub Pages.

Custom domain decision deferred — `livefolio.github.io/sdk` is fine for v0.4. A custom domain is cosmetic and can be added later without changing the build.

## Out of scope

- **Versioned docs** (a separate site for each minor release). v0.4 is the only published version; defer multi-version until a v0.5 ships.
- **A "search the docs" backend beyond what VitePress ships** (which is local index, no external service).
- **Live runnable code samples** (CodeSandbox-style). The harness verifies samples *compile and run in CI*; embedding a live runtime in the page is a different scope.
- **Migration guide from v0.3 to v0.4 in narrative form.** The recipe "Replicating a v0.3 strategy in v0.4" covers the practical case; a comprehensive migration guide would be its own document and isn't gated on phase 8.
- **A fourth agent skill** for cross-cutting concerns (e.g., "livefolio-architecture-explainer"). Three skills is the right starting point; add more reactively if a recurring need surfaces.

## Risks

- **Site bit-rot.** Narrative pages drift from API behavior over time. Mitigation: every code block is an included file under `scripts/docs/`, so syntax/semantic drift breaks `npm run docs:check`. Conceptual drift (a guide says "do X" but the recommended pattern has changed) requires periodic review — own this as part of release-prep checklist for future minors.
- **TSDoc audit churn.** The first pass adds comments to ~80+ exported symbols. This is a substantial diff; review effort matters. Mitigation: split TSDoc audit into per-module sub-tasks (one task per `src/*/` subdirectory) so each PR is reviewable in isolation.
- **TypeDoc + VitePress integration friction.** `vitepress-plugin-typedoc` is third-party and may have versioning issues. Mitigation: pin the plugin version explicitly; if integration breaks on a future VitePress upgrade, fall back to running TypeDoc as a pre-build step that emits markdown into `docs-site/api/`.
- **Skill-vs-doc duplication.** Skills are easy to over-stuff with content that belongs in the docs. Mitigation: each skill body has a hard ceiling of ~100 lines; anything longer means "extract to docs and link from the skill."
- **GitHub Pages deploy flakiness.** Pages occasionally fails for non-obvious reasons (cache, branch protection). Mitigation: the deploy workflow is small and inspectable; fix forward as needed. Not a blocker for landing the docs themselves.
