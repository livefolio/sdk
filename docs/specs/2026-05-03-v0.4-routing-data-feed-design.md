# RoutingDataFeed — multi-source DataFeed composition

**Status:** Design
**Date:** 2026-05-03
**Scope:** v0.4 SDK reference implementation

## Motivation

Tactical strategies need data from more than one vendor. `tactical/v1` requires:

- NYSE/NASDAQ equity bars from Yahoo (`@livefolio/yfinance`)
- Macro time series (yields, CPI, unemployment) from FRED (planned `@livefolio/fred`)

A given asset is served by exactly one vendor — Yahoo carries equities, FRED carries macro series, neither overlaps. Future asset classes (futures, paid equity feeds) will follow the same pattern. Options will eventually need a different surface entirely (chains, Greeks); they are out of scope here.

The v0.4 SDK currently accepts a single `DataFeed` everywhere — `RunBacktestOptions.dataFeed`, `FeatureRuntime` constructor, `BacktestExecutor` constructor. Users wanting multiple feeds must hand-roll a routing wrapper. This spec ships that wrapper as a tested reference implementation.

## Prerequisite — `Asset` becomes a discriminated union

`src/interfaces/types.ts` currently defines `Asset` as a single-variant object literal with `kind: 'equity'` (the JSDoc already flags that other kinds will be added). The routing scheme requires `Asset` to be a true discriminated union so consumers can declare non-equity assets without type errors.

This spec adds one new variant to support FRED:

```ts
export type EquityAsset = {
  kind: 'equity';
  id: AssetId;
  symbol: string;
  exchange?: string;
};

export type MacroAsset = {
  kind: 'macro';
  /** FRED series ID, e.g. 'DGS10', 'CPIAUCSL'. */
  id: AssetId;
  /** Human-readable label, e.g. '10Y Treasury', 'CPI'. */
  symbol: string;
  /** Data provider tag, e.g. 'FRED'. Optional. */
  source?: string;
};

export type Asset = EquityAsset | MacroAsset;
```

`AssetId` stays `string`. Future kinds (`'futures'`, `'option'`, `'crypto'`) follow the same pattern — each is a separate variant added to the `Asset` union when its feed package lands.

**Impact on existing code:** any `Asset` consumer that read `asset.exchange` or assumed equity-only fields needs a `kind === 'equity'` narrow. A pre-implementation grep across `src/` will catch these. They are expected to be few — `Asset` is mostly opaque in the current SDK.

**This change is part of this spec's implementation.** Without it the router cannot be typed correctly.

## Non-goals

- **No interface changes** to `DataFeed`, `runBacktest`, `fromSpec`, `runLive`, `FeatureRuntime`, `BacktestExecutor`, or `Executor`. The router is a `DataFeed` like any other.
- **No streaming router.** A streaming counterpart (`RoutingStreamingDataFeed`) has its own design at `docs/specs/2026-05-03-routing-streaming-and-polling-design.md` (companion plan `docs/plans/2026-05-03-routing-streaming-and-polling.md`); kept out of this spec to keep historical-side scope contained.
- **No options/chains support.** Options need a new interface (`OptionChainFeed` or similar) and a separate router. Out of scope.
- **No fundamentals/events from the FRED package.** That is the FRED package's concern, not this spec's.
- **No automatic capability discovery.** The router does not pre-scan inner feeds; capability mismatches surface at call time as clear errors.

## Design

### Class shape

New file: `src/reference/routing-data-feed.ts`. Exports:

- `class RoutingDataFeed implements DataFeed`
- `class RoutingDataFeedError extends Error`

Constructor accepts two forms:

```ts
type RouteMap = Readonly<Record<string, DataFeed>>;       // keyed by Asset['kind']
type RouteFn  = (asset: Asset) => DataFeed | undefined;   // escape hatch

constructor(routes: RouteMap | RouteFn);
```

Map form is the 90% case. Internally normalized to `RouteFn`:

```ts
const route: RouteFn =
  typeof routes === 'function'
    ? routes
    : (a) => routes[a.kind];
```

### Method behavior

| Method | Behavior |
|---|---|
| `bars(asset, range, freq)` | `route(asset)` → delegate. If route returns `undefined`, throw `RoutingDataFeedError` with `asset.kind` and `asset.id` in the message. |
| `fundamentals(asset, t)` | Always defined on the router. Resolve route; if the resolved feed does not implement `fundamentals`, throw `RoutingDataFeedError` naming the kind. |
| `events` | **Not implemented.** The router's prototype does not declare `events`. `'events' in feed === false`. |

### Edge cases

- **Unknown `asset.kind` (map form):** throw at call time. The error message includes `asset.kind` and `asset.id` so the failure is debuggable from a single line.
- **Function form returns `undefined`:** throw. Same error class.
- **Routed feed missing `fundamentals`:** throw. Distinguish "no route for kind" from "route exists but feed lacks method" in the error message.
- **`events()` called:** the method is genuinely absent. Calling `routingFeed.events(...)` is a `TypeError: routingFeed.events is not a function` — the same shape as calling `events` on any vendor that doesn't implement it.

### Why not alternatives

- **Document a recipe, ship no class.** Rejected. The 20-line wrapper has subtle correctness concerns (forwarding `freq`, handling `fundamentals`/`events` correctly) and would be duplicated across users.
- **First-class `dataFeed: DataFeed | DataFeed[]` in `runBacktest`.** Rejected. Cascades through `BacktestExecutor` and `FeatureRuntime` constructors, hard-codes a single routing rule, and gains nothing the composition pattern doesn't already give us.
- **Fan-out `events()` across all map-form feeds.** Rejected for v1. Asymmetric behavior between map and function forms; tactical/v1 has no consumer for events; can be added non-breakingly if a real use case appears (the optional method goes from absent to present).
- **Capability introspection at construction.** Rejected. Adds construction-time complexity, drifts if feeds are mutated, and gives nothing call-time errors don't.

## Tests

Co-located file `src/reference/routing-data-feed.test.ts`, Vitest, mocked inner feeds via `vi.fn()`:

1. Map form routes by `asset.kind` — equity asset hits the Yahoo mock; macro asset hits the FRED mock.
2. Function form routes via predicate.
3. `bars` forwards `range` and `freq` arguments unchanged to the routed feed.
4. `bars` yields entries in the order the inner feed yields them (no aggregation, no buffering).
5. `fundamentals` routes by kind and forwards `t`.
6. `fundamentals` throws `RoutingDataFeedError` when the routed feed lacks the method (named distinctly from the "no route" case).
7. Unknown `asset.kind` (map form) throws `RoutingDataFeedError` mentioning `asset.kind` and `asset.id`.
8. Function form returning `undefined` throws `RoutingDataFeedError`.
9. `'events' in routingFeed === false`.

## Future considerations (explicitly deferred)

- **Streaming router.** Designed in `docs/specs/2026-05-03-routing-streaming-and-polling-design.md` (no longer "future") — `RoutingStreamingDataFeed` mirrors this constructor surface, paired with a generic `pollingStreamFromHistorical` adapter for vendors without native streaming.
- **`events()` fan-out.** If a consumer materializes, add fan-out + k-way merge (map form only); document function-form limitation.
- **Options.** Separate interface (`OptionChainFeed`) and separate router (`RoutingOptionChainFeed`). Will not share code with `RoutingDataFeed` — different semantics.
