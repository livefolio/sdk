# v0.4 Multi-Repo and Interface Design

**Status:** Draft
**Date:** 2026-04-29
**Companion to:** [2026-04-28-generalized-strategy-architecture-design.md](2026-04-28-generalized-strategy-architecture-design.md)

## Goal

Define the package layout, interface contracts, and reference implementations for SDK v0.4. v0.4 is a complete overhaul: the Strategy and Below layers from the architecture vision become real, the v0.3 Supabase-coupled handle pattern is retired, and `@livefolio/sdk` becomes an open-source pure-logic library that consumers wire to their own data, execution, and persistence.

Out of scope: the Above (planning) layer. Out of scope: live broker adapters. v0.4 ships the SDK + reference backtest stack + a parity story for v0.3 tactical strategies.

## Non-goals

- Backwards compatibility with v0.3 source. v0.3 → v0.4 is a migration with a codemod, not a drop-in replacement.
- Multi-asset-class fidelity (options, futures, FX). v0.4 covers equity-style assets via a position model that doesn't preclude future expansion.
- Live trading. The Executor interface is designed so a live adapter can be added later without changing the SDK; no live adapter ships in v0.4.
- Persistent storage in the SDK. Storage is a consumer concern.

## Repository and package layout

```
@livefolio/sdk                         OSS, public on npm, MIT/Apache
  ├─ Strategy types and helpers
  ├─ Feature primitives (indicators, signals, transforms)
  ├─ Portfolio / order / position models
  ├─ Interfaces: DataFeed, Executor, FeatureCache, Calendar
  ├─ Reference impls: BacktestExecutor, MemoryFeatureCache,
  │                   InMemoryPortfolio, USEquityCalendar
  └─ tactical/ — convenience layer for v0.3-style rule strategies

@livefolio/adapter-yfinance            OSS, separate repo
  └─ implements DataFeed using Yahoo Finance (free tier)

@livefolio/adapter-<paid-provider>     Private (internal)
  └─ wraps proprietary data sources behind the same DataFeed interface

livefolio-app (hosted product)         Private
  ├─ depends on @livefolio/sdk + paid adapters
  ├─ Postgres-backed FeatureCache and strategy persistence
  ├─ Strategy spec registry + serialization layer
  ├─ Multi-tenant runtime, scheduling, UI
  └─ (future) Above layer: AI-assisted strategy authoring
```

The boundary rule: **anything that talks to a third-party data provider lives outside `@livefolio/sdk`**. Anything that's pure computation — feature math, strategy mechanics, order math, accounting logic — lives inside.

## Inside the SDK

### Module map

| Module | Exports | Notes |
|---|---|---|
| `strategy` | `Strategy`, `manage`, `scan`, `reconcile`, `overlay`, `runBacktest` | Core shape and helpers |
| `features` | `defineFeature`, built-ins (SMA, EMA, RSI, MACD, returns, vol, …), `FeatureGraph` | Pure feature math; no I/O |
| `portfolio` | `Position`, `Portfolio`, `applyFills`, `applyOrders` (projection helper) | Lot-aware accounting |
| `orders` | `Order` union (Open/Close/Adjust/Rebalance), `Fill` | Intent + result types |
| `interfaces` | `DataFeed`, `Executor`, `FeatureCache`, `Calendar` | Consumer contracts |
| `reference` | `BacktestExecutor`, `MemoryFeatureCache`, `InMemoryPortfolio`, `USEquityCalendar` | Defaults; replaceable |
| `tactical` | `fromSpec`, builder API, `RuleTree` types | v0.3 parity layer |

### Strategy authoring

```ts
interface Strategy<F extends Features = Features> {
  universe(t: Date, portfolio: Portfolio): Asset[];
  features(universe: Asset[], portfolio: Portfolio, t: Date): F;
  build(features: F, portfolio: Portfolio, t: Date): Order[];
}
```

Two ways to author:

1. **Code form** — implement `Strategy` directly in TypeScript. Full power, not serializable.
2. **Spec form** — author a JSON spec; the SDK provides hydrators (e.g. `tactical.fromSpec(spec)`) that return a `Strategy`. Serializable, UI-buildable, version-controlled.

The SDK supports both. The hosted product uses spec form. Custom code strategies on the hosted product are a future concern (sandboxed compile/eval).

The tactical convenience layer is a spec dialect: `tactical.fromSpec(ruleTreeSpec)` produces a `Strategy` whose `build` is `reconcile(evaluateRuleTree(features, t), portfolio)`. v0.3 strategies migrate into this dialect.

## Interface contracts

These four interfaces are the seams between the SDK and consumer code. They are the public API for adapter authors and must be stable across minor versions.

### DataFeed

```ts
interface DataFeed {
  bars(asset: Asset, range: DateRange, freq: Frequency): AsyncIterable<Bar>;

  // Optional capability surfaces — adapters declare what they support.
  fundamentals?(asset: Asset, t: Date): Promise<Fundamentals>;
  events?(range: DateRange, kinds: EventKind[]): AsyncIterable<Event>;
  // optionsChain?, dividends?, splits? — added as the position model grows
}
```

Adapters return data; the SDK does not assume a particular provider semantics. Time stamps are normalized to UTC; the SDK trusts the adapter to deliver point-in-time-correct values (no look-ahead).

### Executor

```ts
interface Executor {
  submit(orders: Order[], t: Date, portfolio: Portfolio): Promise<Fill[]>;
}
```

The strategy emits orders; the executor decides how they fill. `BacktestExecutor` (reference impl) fills at next-bar open with configurable slippage. A live broker adapter implements the same interface.

### FeatureCache

```ts
interface FeatureCache {
  get(key: FeatureKey): Promise<Series | undefined>;
  set(key: FeatureKey, series: Series): Promise<void>;
  invalidate?(prefix: Partial<FeatureKey>): Promise<void>;
}

type FeatureKey = {
  feature: string;       // e.g. "sma"
  paramsHash: string;    // content hash of params
  scope:
    | { kind: 'asset'; asset: AssetId }
    | { kind: 'universe'; universeHash: string };  // for cross-asset features
  range: DateRange;
  freq: Frequency;
};
```

Keys are content-addressed: same feature + params + scope + range + freq must always produce the same series, so cache hits across strategies and runs are safe. The SDK ships `MemoryFeatureCache` as the default; persistent impls live in consumer packages.

**On `scope`:** v0.4 only emits `kind: 'asset'` keys (tactical features are all per-asset). The `universe` variant is reserved for future cross-asset features (covariance matrices, cross-sectional ranks, sector-relative z-scores) where the value is a function of a *set* of assets, not a single one. Locking the discriminator in now means adding those features later doesn't invalidate every cached series — additive, not breaking.

### Calendar

```ts
interface Calendar {
  isOpen(t: Date): boolean;
  next(t: Date): Date;
  previous(t: Date): Date;
  sessions(range: DateRange): Date[];
}
```

Pluggable so non-US-equity asset classes don't have to fight the default. `USEquityCalendar` ships as a reference impl.

## Reference implementations

These ship inside `@livefolio/sdk` so a backtest works out of the box with no external services:

- **`BacktestExecutor`** — fills at next session open, configurable slippage (bps + fixed), no partial fills, no borrow.
- **`MemoryFeatureCache`** — `Map`-backed, in-process, no eviction. Sufficient for backtest workloads on a laptop.
- **`InMemoryPortfolio`** — single-account, lot-aware ledger; applies `Fill[]` to update positions and cash.
- **`USEquityCalendar`** — NYSE sessions, half-days, holidays.

These are intentionally minimal. Consumers replace them as needs grow.

## Strategy serialization

**Decision:** the SDK supports both code-form (TypeScript `Strategy` implementations) and spec-form (JSON, hydrated by SDK-provided hydrators). Spec-form is opt-in per strategy family via *dialects*.

**Rationale:** the OSS SDK shouldn't force users into JSON specs — code-first authoring is more powerful and idiomatic for library users. But the hosted product needs serialization, and the v0.3 fluent API is already essentially a serializable graph. Shipping `tactical.fromSpec` covers v0.3 parity and gives the hosted product its strategy format for free.

### How serialization actually works

`Strategy.build` is arbitrary code — it can't be serialized in the general case. The trick is that **for any given strategy family, `build` follows a fixed pattern**, and that pattern is what the SDK ships. The user serializes the *inputs to the pattern* (universe, features, rule tree, weights), not the pattern itself.

For tactical strategies the pattern is:

```
build = (features, portfolio, t) => reconcile(evaluateRules(spec.rules, features), portfolio)
```

The user describes:

- which assets are in scope (`universe`),
- which features to compute and their parameters (`features`),
- the decision tree that maps feature values to target weights (`rules`).

The SDK provides `evaluateRules` and `reconcile`. Result: a `Strategy` whose `build` is real code, but the *behavior* is fully determined by the spec.

### Tactical dialect (sketch)

```ts
type TacticalSpec = {
  kind: 'tactical/v1';
  universe: AssetRef[];
  features: FeatureSpec[];          // stable ids referenced by rules
  rules: RuleNode;                  // decision tree → target weights
};

type FeatureSpec =
  | { id: string; kind: 'sma';    asset: AssetRef; period: number }
  | { id: string; kind: 'rsi';    asset: AssetRef; period: number; hysteresis?: number }
  | { id: string; kind: 'price';  asset: AssetRef }
  | { id: string; kind: 'return'; asset: AssetRef; period: number };

type RuleNode =
  | { op: 'allocate'; weights: Record<AssetId, number> }
  | { op: 'if'; cond: Comparison; then: RuleNode; else: RuleNode };

type Comparison = {
  op: 'gt' | 'lt' | 'gte' | 'lte';
  left:  FeatureRef | number;
  right: FeatureRef | number;
};
```

Hydration:

```ts
function fromSpec(spec: TacticalSpec): Strategy {
  return {
    universe: () => spec.universe,
    features: (u, p, t) => evaluateFeatureSpecs(spec.features, u, t),
    build:    (f, p, t) => reconcile(evaluateRuleTree(spec.rules, f), p),
  };
}
```

### Mental model

A spec dialect is a tiny domain-specific language scoped to one strategy family. JSON is the syntax tree. The hydrator is the interpreter. The output is a `Strategy`. The dialect is intentionally not Turing-complete; arbitrary computation requires dropping to code form.

### Extensibility

Future strategy families that benefit from serialization ship their own dialects:

- `riskparity/v1` — universe + covariance source + solver params.
- `xs-momentum/v1` — universe selector + ranking feature + top-N + rebalance cadence.
- `glidepath/v1` — date-indexed weights schedule.

Each dialect is `{ schema, hydrator }`. The SDK exposes a registry; the hosted product enables the dialects it supports. Consumers can author and register their own dialects without forking the SDK.

### Versioning

The `kind` field carries the dialect version (`tactical/v1`). Adjacent versions can coexist; deprecation goes through a window where both hydrators are registered. Specs persist with their version stamped in; the hosted product's storage layer keeps that field intact.

### Custom features inside a dialect

If a tactical strategy needs a feature outside the built-in `FeatureSpec` union, two options:

1. **Versioned dialect change** — add a new `FeatureSpec` variant; bump to `tactical/v2`.
2. **Drop to code form** — implement `Strategy` directly with whatever feature math is needed.

We deliberately don't add a "user-supplied JS expression" escape hatch inside the spec — that re-introduces the unsafe-deserialization problem the spec exists to avoid.

### v0.3 codemod

Each v0.3 fluent-API operation has exactly one `TacticalSpec` mapping. The codemod walks the v0.3 source AST, emits the spec JSON, and the parity test asserts that running the spec via `tactical.fromSpec` over the yfinance adapter produces the same allocation history as the v0.3 strategy on the same range.

### Spec format stability

Dialect specs are part of the public SDK API. Schema changes follow semver: additive optional fields are minor; breaking renames or removals are major and require a new dialect version (`tactical/v2`).

## Feature caching

**Decision:** `FeatureCache` interface in the SDK; `MemoryFeatureCache` as the default; persistent backends are consumer code.

**Rationale:** the SDK can't assume an operational stack. But every consumer needing to design feature cache keys from scratch would be hostile. The interface defines key semantics (content-addressed) and contract; implementations are storage choices.

**Cache scope:** the SDK runtime threads a `FeatureCache` through `runBacktest`. Strategy authors don't manage caching directly — they declare features, the runtime caches series under content-addressed keys. Cross-strategy reuse comes for free if the same `FeatureCache` instance is shared.

## Forward compatibility

v0.4 ships equity-tactical only, but the architecture is intended to absorb additional strategy families and asset classes without redesigning the strategy authoring surface. This section documents what each future expansion is expected to touch and which seams are reserved now to avoid forced rework.

### Where each expansion lands

| Expansion | What changes | What stays |
|---|---|---|
| Other equity strategies (TLH, momentum, risk-parity) | New dialects + `FeatureSpec` kinds (covariance, rank, fundamentals); `DataFeed.fundamentals` adapters | `Strategy` interface, helpers, `Order`/`Position`, executors |
| Options | `Asset` gains an Option variant; `Position.legs/strike/expiry` activate; `DataFeed.optionsChain/iv/greeks` capability; new dialect (`coveredcall/v1`); options-aware backtest executor (assignment, exercise, expiry) | `Strategy` interface, helpers, `Order` envelope, `FeatureCache`, `Calendar` |
| Futures | Margin-aware `Portfolio` (mark-to-market, variation margin, settlement cash flow); continuous-contract handling in adapter; futures-aware executor | `Strategy` interface, helpers, `Order` envelope |
| Cross-asset combinations | `Asset` returned from `universe` is a union; features are family-namespaced; one `Portfolio`, one `build` | Composition pattern (helpers in sequence inside `build`) |

The pattern is consistent across all four: **interfaces don't break, implementations grow, dialects accumulate.**

### Reserved seams

Two structural decisions are made in v0.4 *specifically* to keep future expansions additive rather than breaking. Neither requires implementation work in v0.4 — only that the shape is reserved.

1. **`FeatureKey.scope` discriminator** — already documented in the FeatureCache section above. v0.4 only emits `kind: 'asset'`; the `kind: 'universe'` variant is reserved for cross-asset features.

2. **Portfolio event channel (`PortfolioEventFeed`)** — `Executor` returns `Fill[]` *in response to orders*. But options assignment, expiry, dividends, splits, futures settlement, and corporate actions change the portfolio **without** a `Strategy.build` call. They will need a separate ingest path:

   ```ts
   interface PortfolioEventFeed {
     events(range: DateRange, portfolio: Portfolio): AsyncIterable<PortfolioEvent>;
   }

   type PortfolioEvent =
     | { kind: 'split'; asset: AssetId; ratio: number; t: Date }
     | { kind: 'dividend'; asset: AssetId; amountPerShare: number; t: Date }
     | { kind: 'assignment'; positionId: PositionId; t: Date }
     | { kind: 'expiry'; positionId: PositionId; t: Date }
     | { kind: 'settlement'; ... };
   ```

   v0.4 does **not** implement this. Equity-only v0.4 backtests assume splits and dividends are baked into adjusted bars from the data adapter (a known limitation, captured in Open Questions). The interface is reserved here so that adding the channel when options arrive doesn't reshape the runtime loop.

### Explicitly *not* pre-designed

These additions are deferred entirely. Adding them when needed is additive, so pre-designing them now would be over-reach:

- Margin / mark-to-market accounting (futures-time concern).
- Multi-leg order envelopes (options-time concern).
- Greeks / IV / chain queries on `DataFeed` (options-time concern; capability surface is already optional).
- Composite dialect for spec-form combinations (deferred until the second dialect ships).
- Asset-class-specific calendars beyond `USEquityCalendar` (the `Calendar` interface is already pluggable).

### Combinations across families

The architecture vision's combination story (e.g. "tactical + covered call") composes inside a single `Strategy.build` calling helpers in sequence — `manage` for position lifecycle, `reconcile` for target weights, `scan` for new positions, `overlay` for portfolio-wide constraints. Call order resolves precedence; `applyOrders(portfolio, orders)` projects state between steps so each helper sees the post-prior-step view.

In **code form**, combinations are available the moment the relevant features and helpers exist. In **spec form**, combinations require a `composite/v1` dialect (deferred until the second family ships). v0.4 ships neither the helpers' multi-asset-class support nor the composite dialect — but the strategy authoring surface is the same one that will host them.

## v0.3 → v0.4 migration

### Parity case

Pick one representative v0.3 tactical strategy (TBD, but a multi-rule allocation across ≥ 3 tickers with at least one signal-driven branch). The migration is complete when:

1. The same strategy expressed as a `TacticalSpec` and run via `runBacktest` over the same date range with the yfinance adapter,
2. Produces an allocation history that matches the v0.3 output bar-for-bar, allowing only documented differences (e.g. calendar handling, fill price convention).

This is the v0.4 "are we done" gate.

### User migration path

- Provide a `livefolio migrate` CLI codemod that reads a v0.3 fluent-API strategy file and emits a `TacticalSpec` JSON.
- Document the spec dialect.
- Ship a "before / after" example in the SDK README.

The v0.3 Supabase schemas are abandoned in v0.4. Existing hosted-product data needs a separate migration owned by the hosted product, not the SDK.

## Open questions

- **Async vs sync feature compute.** Pricing data fetch is async; pure indicator math is sync. Likely answer: feature DAG nodes are async by default; sync nodes are auto-promoted.
- **Multi-frequency strategies.** A strategy that uses both daily and intraday data — does it run on the intraday clock with daily features cached, or does the runtime support multiple clocks? Defer until a real use case.
- **Corporate actions.** Splits and dividends — are they delivered through `DataFeed` (adjusted bars) or as a separate event stream that the accounting layer applies? Affects backtest fidelity.
- **Strategy-level state.** `Strategy` as written is stateless (state lives in `Portfolio`). Some strategies want auxiliary state (e.g. last rebalance date, regime label). Solution sketch: state is part of `Portfolio.tags` or a `state` slot the runtime threads through.
- **Calendar binding.** One calendar per backtest, or per-asset calendars? Equities-only v0.4 can defer.
- **Codemod fidelity.** What v0.3 features does the codemod cover, and what's a manual port?

## Effort estimate

Rough phases (not a plan — the plan doc lives separately):

1. Core types + interfaces + reference impls (Strategy, Order, Position, Portfolio, BacktestExecutor, MemoryFeatureCache, USEquityCalendar). Foundation; everything else depends on this.
2. Feature library port (indicators, signals, transforms) onto the new feature-graph runtime, with the FeatureCache integration.
3. Tactical dialect (`TacticalSpec`, `fromSpec`, rule-tree evaluator) — the v0.3 parity surface.
4. yfinance adapter (separate repo) — implements DataFeed enough to drive parity tests.
5. Parity test against a chosen v0.3 strategy — must match before v0.4 ships.
6. Codemod + migration docs.

Each phase gets its own spec + plan in `docs/`.
