# v0.4 Phase 9 — Streaming runtime, live evaluation, and chart continuity

**Status:** Draft (discussion captured 2026-05-02; no implementation work started)
**Companion plan:** TBD (write when ready to implement)
**Depends on:** v0.4.0 ships from PR #29

## Goal

Let consumer apps render a strategy's historical backtest snapshots and live-evaluated snapshots on a single continuous chart. Strategy code stays the same across both modes — only the runtime that drives it changes.

The shipping shape we're aiming for:

```
[ historical run via runBacktest ]──┬──[ live run via runLive ]──> chart
                                    │
                              shared portfolio state
                              shared strategy state
```

## Non-goals

- Live trading **execution** primitives (`Executor` impls for real brokers). v0.4's `Executor` interface already handles this; concrete adapters are vendor-specific work, not Phase 9.
- Multi-account / portfolio aggregation across strategies. That's the "planning layer" from `2026-04-28-generalized-strategy-architecture-design.md` and explicitly future.
- A WebSocket data feed for Yahoo Finance specifically. The interface needs to support streaming feeds; concrete WS adapters (Coinbase, Polygon, Alpaca, etc.) ship in their own repos under the `repo=vendor / package=interface` convention.

## The four design decisions made in conversation

### 1. Split `DataFeed` into `HistoricalDataFeed` and `StreamingDataFeed`

Today's `DataFeed` lumps `bars()` (historical, range-bounded) onto a single interface. v0.4 reserved `subscribe()` as a future-optional method on the same interface. We're rejecting that union.

**Why:** vendor SDKs split across environments. `yahoo-finance2` is Node-only (REST historical); a websocket data source might be browser-friendly (Coinbase WS) or might need a server-side bridge (Yahoo's unofficial WS, Alpaca). Forcing one adapter class to satisfy both `bars` and `subscribe` means every adapter ends up Node-or-browser-only when the underlying APIs naturally split.

**Decision:**

```ts
interface HistoricalDataFeed {
  bars(asset, range, freq): AsyncIterable<Bar>;
  // optional fundamentals/events stay here
}

interface StreamingDataFeed {
  subscribe(assets, freq): AsyncIterable<Bar>;
}

runBacktest({ dataFeed: HistoricalDataFeed, ... })
runLive({ dataFeed: StreamingDataFeed, ... })
```

Each runtime accepts its own interface. App composes by passing the right adapter to the right runtime.

### 2. No composition helper

Originally sketched a `combineDataFeeds({ historical, streaming })` helper. **Rejected** as YAGNI — it's just `{ ...a, ...b }` at the call site, no abstraction value.

If a real composition pattern emerges later (e.g. "fall back to polling `bars` when `subscribe` is missing"), THAT specific helper can ship. But not a generic combiner.

### 3. `runLive` runtime primitive

A small async-generator counterpart to `runBacktest`. ~100 lines, mechanical:

```ts
async function* runLive({ strategy, dataFeed, executor, calendar, initialPortfolio }) {
  let portfolio = initialPortfolio;
  for await (const bar of dataFeed.subscribe(universe, freq)) {
    if (!calendar.isOpen(bar.t)) continue;
    const features = await strategy.features(universe, portfolio, bar.t);
    const orders = strategy.build(features, portfolio, bar.t);
    const fills = await executor.submit(orders, bar.t);
    portfolio = applyFills(portfolio, fills);
    yield { t: bar.t, portfolio, orders, fills }; // BacktestSnapshot shape
  }
}
```

Yielded snapshots are **identical in shape** to `BacktestSnapshot[]` from `runBacktest`. Consumer concatenates `[...history.snapshots, ...liveSnapshots]` for one continuous chart.

### 4. State continuity strategy: replay-then-stream (the hack), with proper API as future work

**The problem:** Today, strategy auxiliary state (hysteresis comparators, last rebalance date) lives in JS closures inside `fromSpec`. When historical ends and live starts, a fresh `fromSpec` instance has no prior state — first live rebalance behaves wrong.

**The 80% solution (ships in Phase 9):** keep the same `Strategy<F>` instance across history and live. Replay history first, which walks every session in order and warms up the closure state. Then start `runLive` with that hot instance. Works because `fromSpec`'s closures persist between `build()` calls.

```ts
const strategy = fromSpec(spec, { runtime, calendar });
const history = await runBacktest({ strategy, range: [inception, now], ... });
// strategy's closures are now in the right state for live mode
for await (const snap of runLive({ strategy, initialPortfolio: history.finalPortfolio, ... })) { ... }
```

**The 20% gap (deferred):** cross-process resume. Need `Strategy<F>.getState()` / `setState()` (or runtime-threaded state in the `build` signature). Required for: pausing a backtest and resuming later, surviving server restarts in production live mode, fast-forwarding a strategy without replaying history. None of these block the basic "chart shows historical + live" UX.

When this needs to be built, the cleanest interface is probably:

```ts
interface Strategy<F, S = unknown> {
  universe: ...;
  features: ...;
  build(features: F, portfolio: Portfolio, state: S, t: Date): { orders: Order[], state: S };
  initialState(): S;
}
```

State is JSON-serializable. Runtime threads it through. Hysteresis closures inside `fromSpec` get refactored to read from / write to the threaded state. Backward-compat is maintained by defaulting `S = void` and treating `state`-less strategies as state-of-undefined.

## Mark-to-market is an app concern, not an SDK primitive

The chart needs two streams:

| Stream | Cadence | Source |
|---|---|---|
| Strategy snapshots | Once per rebalance (e.g. weekly) | `runLive` yields |
| Mark-to-market re-valuation | Every tick (intra-day) | App-side: subscribe to `StreamingDataFeed`, recompute NAV from latest snapshot's positions |

The SDK provides the primitives (`StreamingDataFeed.subscribe`, `Position` types). App glues them together for the "wiggling rightmost point" UX. No SDK-level helper needed — the math is `cash + sum(positions.map(p => p.quantity * tick.price(p.asset)))`.

## Calendar binding — separate concern, related decision

Crypto strategies (BTC-USD via yfinance) work "well enough" on the NYSE calendar for weekly+ rebalance cadences. Known approximation: under-samples by ~30% (NYSE has ~252 sessions/yr; BTC has ~365). Vol estimates and short-period SMAs become slightly wrong.

**Provisional decision for v0.5:** ship a `Crypto24x7Calendar` (every day a session) for crypto-only strategies. Per-asset calendars (the proper "Calendar binding" fix) stays deferred until a strategy genuinely spans US equities + crypto in the same backtest.

`Crypto24x7Calendar` is trivial — implements `Calendar`, every day is `isOpen=true`, `next(t)` is `t + 1 day`, `previous(t)` is `t - 1 day`, sessions are 24h or whatever convention the strategy needs. Probably 50 lines.

## Effort estimate

If implementing as one phase:

| Task | Effort |
|---|---|
| Split `DataFeed` → `HistoricalDataFeed` + `StreamingDataFeed`; update `runBacktest` signature | Small — additive, backward-compat alias keeps `DataFeed = HistoricalDataFeed` |
| `runLive` runtime + tests | Medium |
| `Crypto24x7Calendar` reference impl + tests | Small |
| Document the replay-then-stream pattern in docs site (recipe) | Small |
| First streaming reference adapter (Coinbase WS for BTC) — separate repo | Medium — vendor work in `coinbase/` sibling repo |
| Strategy state API (`getState`/`setState`, runtime threading) | Medium — interface change with backward compat |

Probably 2-3 weeks if doing all of it. Most of the value lands in the first three rows.

If splitting into Phase 9a and 9b:

- **9a:** interface split + `runLive` + `Crypto24x7Calendar` + replay-then-stream recipe. Ships the 80% UX.
- **9b:** strategy state API. Ships when the cross-process / fast-forward use cases get real.

## Open questions

- **What's the right websocket adapter to ship as the reference?** Coinbase (browser-friendly, BTC-only) is the easiest start. Polygon (multi-asset, browser SDK exists) is more general but requires API key. Alpaca (US equities + crypto, browser-friendly) is the natural pair if the user's stack already has Alpaca. Decision deferred until Phase 9 starts.
- **Bar aggregation across timescales:** if streaming gives ticks but strategy is daily, who aggregates? Probably the streaming adapter (e.g. `CoinbaseWSFeed({ aggregate: '1d' })`), not the runtime. Open.
- **Re-entry semantics:** if `runLive` is interrupted and restarted, does it resume from the last snapshot or from inception? With the "same strategy instance" pattern, only resume-from-snapshot works (closures are in-process). Cross-process resume needs the state API.
- **Mark-to-market intra-bar — does the SDK help?** Probably ship a small `valuePortfolio(portfolio, priceLookup)` helper since every consumer will reimplement it. Borderline YAGNI; revisit after the first consumer integration.

## What this spec is NOT

- Not a migration story for v0.3's `previewLive`-style API (that was a different shape, lived inside the v0.3 client).
- Not a real-broker-adapter spec — `Executor` is already the right interface; live brokers are vendor work.
- Not a portfolio-accounting upgrade — `applyFills` already does the math. Phase 9 doesn't change accounting.
