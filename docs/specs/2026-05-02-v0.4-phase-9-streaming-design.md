# v0.4 Phase 9 — Streaming runtime, live evaluation, and chart continuity

**Status:** Draft (discussion captured 2026-05-02 / refined 2026-05-03; no implementation work started)
**Companion plan:** TBD (write when ready to implement)
**Depends on:** v0.4.0 ships from PR #29

## Goal

Let consumer apps render a strategy's historical backtest snapshots and live-evaluated snapshots on a single continuous chart. Strategy code stays the same across both modes — only the runtime that drives it changes.

The shipping shape we're aiming for:

```
[ historical run via runBacktest ]──┬──[ live run via runLive ]──> chart
                                    │
                              shared portfolio state
                              shared strategy state
```

## Non-goals

- Live trading **execution** primitives (`Executor` impls for real brokers). v0.4's `Executor` interface already handles this; concrete adapters are vendor-specific work, not Phase 9.
- Multi-account / portfolio aggregation across strategies. That's the "planning layer" from `2026-04-28-generalized-strategy-architecture-design.md` and explicitly future.
- A WebSocket data feed for Yahoo Finance specifically. The interface needs to support streaming feeds; concrete WS adapters (Coinbase, Polygon, Alpaca, etc.) ship in their own repos under the `repo=vendor / package=interface` convention.
- **Async vs sync feature compute** (a separate reserved seam from the v0.4 design spec). This is a backtest performance optimization — sequential awaits inside `evaluateFeatureSpecs` are slow in both backtest and live, but fixing it has nothing to do with live evaluation. Belongs in a future "Feature DAG and parallelism" phase when performance becomes a real complaint.
- **Multi-frequency strategies** (another reserved seam — strategies that read both daily and intraday data). The driver is "two clocks in one strategy," not "live vs historical." Multi-frequency exists as a problem in pure backtest mode too (daily SMA + 5-min vol overlay). Belongs in its own future phase when a concrete use case lands.

Phase 9 covers the live-evaluation seams: streaming feed split, runtime-driven tick aggregation, mark-event preview-build, calendar for crypto, and the strategy state API (originally deferred to a 9b, pulled into 9 once preview-build forced it). The other two reserved seams — async/sync features and multi-frequency — share the "deferred until driven by use case" bucket but are independent of streaming. Lumping them in would turn Phase 9 into a "fix every open question at once" mega-phase that's hard to ship incrementally.

## The four design decisions made in conversation

### 1. Add `StreamingDataFeed` as a sibling of `DataFeed`

Today's `DataFeed` has `bars(asset, range, freq)` — historical, range-bounded. v0.4 reserved `subscribe()` as a future-optional method on the same interface. We're rejecting that union.

**Why:** vendor SDKs split across environments. `yahoo-finance2` is Node-only (REST historical); a websocket data source might be browser-friendly (Coinbase WS) or might need a server-side bridge (Yahoo's unofficial WS, Alpaca). Forcing one adapter class to satisfy both `bars` and `subscribe` means every adapter ends up Node-or-browser-only when the underlying APIs naturally split.

**Decision:** keep `DataFeed` as-is (it already means "historical" — it has `bars(range, freq)`) and add a new sibling interface for streaming. No rename, no backward-compat alias, no churn for existing callers / reference impls / parity workspace.

```ts
// Existing — unchanged.
interface DataFeed {
  bars(asset, range, freq): AsyncIterable<Bar>;
  // optional fundamentals/events stay here
}

// New.
interface StreamingDataFeed {
  subscribe(assets, freq): AsyncIterable<Bar>;
}

runBacktest({ dataFeed: DataFeed, ... })
runLive({ dataFeed: StreamingDataFeed, ... })
```

Each runtime accepts its own interface. App composes by passing the right adapter to the right runtime. A vendor that offers both (Polygon, Alpaca) implements both interfaces on one class; consumers pass the same instance to both runtimes, and each runtime sees only its own interface. No union type involved.

Naming is asymmetric on purpose: `DataFeed` is the baseline that already exists in the codebase and in published v0.4.0; `StreamingDataFeed` is the additional capability with a self-describing name.

### 2. No composition helper

Originally sketched a `combineDataFeeds({ historical, streaming })` helper. **Rejected** as YAGNI — it's just `{ ...a, ...b }` at the call site, no abstraction value.

If a real composition pattern emerges later (e.g. "fall back to polling `bars` when `subscribe` is missing"), THAT specific helper can ship. But not a generic combiner.

### 3. `runLive` runtime primitive

`runLive` is an async generator that consumes a tick stream from `StreamingDataFeed.subscribe` and yields a unified `LiveEvent` stream with two variants — `mark` (per-tick revaluation + preview of what the strategy would do at close) and `snapshot` (per-session-close commit, identical shape to `BacktestSnapshot`).

```ts
type LiveEvent =
  | {
      type: 'mark';
      t: Date;
      portfolio: Portfolio;          // current real-time NAV
      prices: Map<Asset, number>;    // latest tick prices
      features: Features;            // indicators with current price as latest "close"
      previewOrders: Order[];        // what strategy.build WOULD emit at close
      previewPortfolio: Portfolio;   // post-rebalance NAV if those orders filled
    }
  | {
      type: 'snapshot';              // committed at session close — same shape as BacktestSnapshot
      t: Date;
      portfolio: Portfolio;
      orders: Order[];
      fills: Fill[];
    };

async function* runLive({ strategy, history, dataFeed, executor, calendar }): AsyncIterable<LiveEvent>;
```

**The runtime owns aggregation, the adapter is dumb.** `StreamingDataFeed.subscribe(assets)` emits raw ticks at whatever cadence the vendor provides (Yahoo WS, for instance, emits 24/7 including outside session hours). The runtime — which knows the strategy's freq and has the calendar — decides for each tick:

- **Tick within current session** → emit `mark` event: extend the current bar's "close" to the latest price, recompute features, run `strategy.build` in preview mode, emit revaluation + preview orders.
- **Tick crosses session boundary** (calendar says session has closed and a new one opened) → finalize the just-closed bar, append it to the historical buffer, recompute features for the closed bar, run `strategy.build` for real, submit orders to executor, apply fills, emit `snapshot`. Then start accumulating the next session's bar from this tick.
- **Tick outside any session** (after-hours, weekend for non-24/7 calendars) → emit `mark` against the still-frozen last snapshot, no new bar accumulation.

This puts calendar logic in one place (the runtime) instead of forcing every WS adapter to know about session boundaries. Vendor adapters stay trivial: connect, subscribe, emit ticks. For 24/7 markets (`Crypto24x7Calendar`), every tick is in-session and the boundary check trivially rolls at midnight UTC (or whatever convention the strategy needs).

**Preview-build safety requires the state API.** Running `strategy.build` on every tick (for `previewOrders`) would corrupt closure-based hysteresis state — by session close, the real `build` call would see state that's been "advanced" by every preview tick in between. This is why the strategy state API (decision #4) ships in Phase 9, not deferred: preview-build snapshots state before the call and restores it after, so previews are non-destructive. Without the state API, preview orders cannot ship safely for stateful strategies.

Consumers concatenate `history.snapshots` with the `snapshot`-typed events for one continuous chart, and consume `mark` events for the wiggling rightmost point + "what would happen at close" preview.

### 4. Strategy state API: threaded, JSON-serializable state on `build`

**Originally** this was the deferred "20% gap" — Phase 9 was going to ship a closure-based hack (replay-then-stream with the same `Strategy<F>` instance) and defer the proper API. **The mark-event preview-build use case forces it into Phase 9 proper.**

**The problem:** strategy auxiliary state (hysteresis comparators, last rebalance date) lives in JS closures inside `fromSpec`. Two failure modes if we keep it that way:

1. **Cross-history seam.** Historical ends and live starts; a fresh `fromSpec` instance has no prior state, so the first live rebalance behaves wrong. Replay-then-stream patches this by reusing the same instance — workable, but only within one process.
2. **Preview-build corruption.** Mark events run `strategy.build` on every tick to compute `previewOrders`. Closure-based hysteresis advances on each call, so by the actual session close, the real `build` sees state that's been "advanced" by every preview tick in between. The real decision is wrong. There is no closure-based workaround for this.

**The decision:** ship a threaded-state interface in Phase 9. State is JSON-serializable; runtime threads it through `build`; preview-build is non-destructive because the runtime can capture state before the preview call and ignore the returned new state.

```ts
interface Strategy<F, S = unknown> {
  universe: (t: Date, portfolio: Portfolio) => Asset[];
  features: (universe: Asset[], portfolio: Portfolio, t: Date) => Promise<F>;
  initialState(): S;
  build(
    features: F,
    portfolio: Portfolio,
    state: S,
    t: Date
  ): { orders: Order[]; state: S };
}
```

State is JSON-serializable so it round-trips through any persistence layer (memory, localStorage, Supabase, Redis). Hysteresis closures inside `fromSpec` get refactored to read from / write to the threaded state. Backward-compat is maintained by defaulting `S = void` and treating `state`-less strategies as state-of-undefined — existing `Strategy<F>` callers compile unchanged.

**`runLive` then becomes:**

```ts
const strategy = fromSpec(spec, { runtime, calendar });
const history = await runBacktest({ strategy, range: [inception, now], ... });
for await (const ev of runLive({
  strategy,
  history,                           // BacktestResult — carries finalPortfolio + finalState + bar buffer
  dataFeed: streamingFeed,
  executor,
  calendar,                          // optional, defensive isOpen check
})) {
  if (ev.type === 'mark') chart.updateLastBar(ev);
  else chart.appendBar(ev);
}
```

**Why `runLive` consumes `BacktestResult`, not `finalPortfolio` + `finalState` separately:** three things have to be warm for the first live tick to behave correctly:

1. **Strategy state** — hysteresis comparators, last rebalance date. Carried as `history.finalState`.
2. **Portfolio** — cash + positions. Carried as `history.finalPortfolio`.
3. **Indicator warmup state** — to evaluate `SMA(SPY, 200)` on the first live tick at time T+1, the FeatureRuntime needs bars from T-199 to T already in its buffer. A fresh streaming-mode FeatureRuntime starting from `finalPortfolio + finalState` alone has no bars and would either return an empty series (silent wrong answer) or refetch the full lookback window from the historical feed (wasteful, and a layering smell — live mode shouldn't depend on the historical feed).

Passing the full `BacktestResult` lets `runLive` seed the streaming FeatureRuntime from the historical bar buffer (or hold a reference to the historical FeatureRuntime for read-through). This also makes the "you must replay first" dependency structural rather than convention — you can't accidentally pass a portfolio + state pair that doesn't match the strategy's warm bar buffer, and indicator continuity at the history/live seam is the runtime's responsibility, not the caller's.

`BacktestResult` therefore needs to expose `finalPortfolio`, `finalState` (the new field), and either retain a reference to the FeatureRuntime that produced it or expose the per-asset bar window it accumulated. Exact carrier shape is an implementation detail for the Phase 9 plan.

**Bonus: cross-process resume falls out for free.** With state threaded and serializable, the original "deferred" use cases — pausing/resuming a backtest, surviving server restarts in production live mode, fast-forwarding without replaying history — work without further design. They're not the driving motivation, but they ship as a side effect.

## Considered and rejected: unified `Engine` + push API

An alternative shape was considered: collapse `runBacktest` and `runLive` into one stateful `Engine` exposing `tick(t)` (and optionally `markToMarket(prices)`), with `runBacktest` kept as a thin wrapper for backward compat.

```ts
class Engine {
  tick(t: Date): BacktestSnapshot;
  markToMarket(prices): Portfolio;
  get snapshots(): readonly BacktestSnapshot[];
}

// runBacktest becomes:
const engine = new Engine(opts);
for (const t of calendar.sessions(range)) await engine.tick(t);
return { snapshots: engine.snapshots, finalPortfolio: engine.portfolio };
```

**Why it's appealing.** The hybrid (replay → live) is the headline Phase 9 UX, and one engine handles it cleanly: `for (date of history) engine.tick(date); ws.on('bar', b => engine.tick(b.t))` produces one continuous snapshot list owned by one object. Mark-to-market wiggle composes naturally on the same instance. The `FeatureRuntime` refactor (open-ended range, incremental bar buffer) is needed either way, so the unified design doesn't add cost there — it just avoids a second loop on top of it. Backward compat is free since `runBacktest` keeps its signature.

**Why we're rejecting it.** Live mode is going to grow complexity that backtest doesn't have: reconnect/resubscribe, gap detection, late-bar reconciliation, watchdog timers. With a unified `Engine`, the temptation is to bolt those on as `engine.onGap()` / `engine.onReconnect()` hooks that mean nothing in backtest. Holding the line — "the engine handles a sequence of ticks; reconnect/gap logic lives in the live driver code that calls `engine.tick`" — is a discipline cost. Keeping `runBacktest` and `runLive` separate is a fence that enforces the separation structurally rather than by convention. The dual-runtime design pays a small ergonomic cost on the hybrid case (two API calls + manual snapshot concatenation) in exchange for that structural guarantee.

If a future revisit shows the live-driver code is genuinely thin and not accumulating reconnect/gap concerns, this decision can flip — the unified Engine is recoverable from dual runtimes.

## Mark-to-market is now an SDK concern (revised)

Earlier draft of this spec said mark-to-market was an app concern and the SDK would only provide the primitives (`StreamingDataFeed.subscribe`, `Position` types) for the consumer to wire up. That was based on the assumption that mark events were just "show NAV wiggle."

The chart UX target is richer: users want to see **what the strategy would do if the session ended now** — preview orders, post-rebalance NAV, indicator values reflecting the latest tick. That requires the FeatureRuntime + strategy to be invoked per tick, which is squarely SDK territory. So `runLive` owns the demux:

| Stream | Cadence | Source |
|---|---|---|
| Strategy snapshots (commit) | Once per session close | `runLive` yields `LiveEvent` with `type: 'snapshot'` |
| Mark-to-market + preview | Every tick (intra-session) | `runLive` yields `LiveEvent` with `type: 'mark'` |

Both come out of the same `AsyncIterable<LiveEvent>`, from the same WS subscription. Consumers don't double-subscribe and don't reimplement NAV math.

## Calendar binding — separate concern, related decision

Crypto strategies (BTC-USD via yfinance) work "well enough" on the NYSE calendar for weekly+ rebalance cadences. Known approximation: under-samples by ~30% (NYSE has ~252 sessions/yr; BTC has ~365). Vol estimates and short-period SMAs become slightly wrong.

**Provisional decision for v0.5:** ship a `Crypto24x7Calendar` (every day a session) for crypto-only strategies. Per-asset calendars (the proper "Calendar binding" fix) stays deferred until a strategy genuinely spans US equities + crypto in the same backtest.

`Crypto24x7Calendar` is trivial — implements `Calendar`, every day is `isOpen=true`, `next(t)` is `t + 1 day`, `previous(t)` is `t - 1 day`, sessions are 24h or whatever convention the strategy needs. Probably 50 lines.

## Effort estimate

Phase 9 ships as **one phase** (no 9a/9b split). The earlier split assumed the strategy state API could be deferred; the mark-event preview-build use case forced it into scope. Once state is being threaded, the cross-process/resume use cases come along for free, so there's nothing left to defer.

| Task | Effort |
|---|---|
| Add `StreamingDataFeed` interface (sibling of existing `DataFeed`) | Trivial — purely additive, no changes to `DataFeed` or existing callers |
| Strategy state API: `Strategy<F, S>` with `initialState` + threaded `state` in `build`; refactor `fromSpec` closures to read/write threaded state; backward-compat default `S = void` | Medium-Large — interface change but additive; `fromSpec` internals refactor is the bulk of the work |
| Streaming `FeatureRuntime` mode: open-ended range, append-only bar buffer, per-tick recompute | Medium |
| Tick → bar aggregation in `runLive`: calendar-driven session boundaries, current-bar accumulator, mark/snapshot demux | Medium |
| `runLive` runtime + `LiveEvent` (mark / snapshot) + preview-build with state snapshot/restore + tests | Medium |
| `BacktestResult` carries `finalState` and bar-buffer lineage for `runLive` consumption | Small |
| `Crypto24x7Calendar` reference impl + tests | Small |
| Document the replay-then-stream pattern + mark-event preview UX in docs site (recipe) | Small |
| First streaming reference adapter (Yahoo WS) — separate repo | Medium — vendor work in `yfinance/` sibling repo |

Probably 4-5 weeks for the SDK work, plus the vendor adapter in parallel. The state API refactor is the new long pole — it touches `fromSpec`, every reference impl, and all hysteresis-bearing strategies in tests.

## Open questions

- **What's the right websocket adapter to ship as the reference?** Yahoo WS is the planned first adapter (matches the existing `yahoo-finance2` historical adapter, no API key, multi-asset). Coinbase, Polygon, or Alpaca remain options for follow-up adapters in their own sibling repos. Selection is vendor work, not an SDK design question.
- **Re-entry semantics:** in-process reconnect (WS drops and resubscribes) is the live-driver code's responsibility — catch the close, resubscribe, optionally request a gap-fill via `dataFeed.bars(lastSeen, now)` and feed it back into the FeatureRuntime before resuming. Cross-process resume works via the state API (serialize `BacktestResult.finalState` + bar buffer somewhere durable, deserialize on restart). Exact contract is an implementation concern for the Phase 9 plan, not a design decision.

### Resolved during design

- **Bar aggregation across timescales** → **runtime aggregates, adapter is dumb.** Original draft nudged toward "streaming adapter aggregates"; reversed in conversation. The adapter emits raw ticks (Yahoo WS streams 24/7 including outside session hours); `runLive` uses the calendar to decide tick-vs-session-boundary and accumulates the current bar internally. Keeps adapters trivial and centralizes calendar logic. See decision #3.
- **Mark-to-market intra-bar — does the SDK help?** → **Yes, subsumed by `LiveEvent.mark`.** Original draft called this borderline YAGNI; the chart UX target ("preview what strategy would do at close") elevated it from optional helper to core SDK responsibility. `runLive` emits `mark` events with portfolio, prices, features, and preview orders. No standalone `valuePortfolio` helper needed — the math lives inside `runLive`. See decisions #3 and #4.

## What this spec is NOT

- Not a migration story for v0.3's `previewLive`-style API (that was a different shape, lived inside the v0.3 client).
- Not a real-broker-adapter spec — `Executor` is already the right interface; live brokers are vendor work.
- Not a portfolio-accounting upgrade — `applyFills` already does the math. Phase 9 doesn't change accounting.
