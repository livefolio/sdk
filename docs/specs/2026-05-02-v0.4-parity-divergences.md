# v0.4 Parity Divergences

Status: codified by `parity/src/parity.test.ts`. Each allowance below is a
structural difference between v0.3 (fluent API + `evaluateStrategy`) and v0.4
(`tactical/v0` spec + `fromSpec` + `runBacktest`) that the parity gate
explicitly accepts. None of these reflect a difference in target weights on
days where both engines emit a target — those agree to floating-point
tolerance.

## Methodology: TARGET-vs-TARGET

Both engines operate over the same yfinance fixture data (SPY/QQQ/IEF
2020 → 2024) and the same canonical strategy (`buildV3Strategy` /
`PARITY_SPEC`). The parity gate compares **target** weights:

- **v0.3 side**: `extractV3History(StrategyBar[])` reads `bar.allocation.holdings`.
  v0.3's `evaluateStrategy` carries the last-rebalance target forward across
  non-rebalance days, so `holdings` *is* the target on every trading day.
- **v0.4 side**: `extractV4TargetHistory({ result, spec, runtime, calendar })`
  re-evaluates the rule tree (`evaluateRuleTree`) with features computed by
  `evaluateFeatureSpecs` at each snapshot date. On rebalance days it computes
  a fresh target; on non-rebalance days it carries the last target forward —
  matching v0.3's semantics.

Comparing realized portfolio weights (`extractV4History`) against v0.3 target
weights generates spurious "diffs" from inter-rebalance price drift. Both
engines compute the same target from the same inputs; comparing targets
isolates the rule-tree semantics from execution-time effects.

## Allowance 1: SMA200 warmup window

**Symptom:** v0.3 emits `IEF=1` (defensive branch) on every trading day from
the start of the comparison range until SMA200 first has a value
(~2020-06-05 → ~2020-10-15). v0.4 emits no allocation during the same window.

**Root cause:** The two engines handle "feature undefined" differently.

- **v0.3**: `evaluateStrategy` (`src/computations/strategy.ts:76`) reads
  `signalSeries.get(id)?.get(date) ?? false`. A missing/undefined signal
  value is coerced to `false`, so the trend rule's `when` clause fails and
  evaluation falls through to the catch-all defensive rule (`hold: ief`).
- **v0.4**: `fromSpec` (`src/tactical/from-spec.ts`) treats undefined features
  as a hard skip — when any feature in `spec.features` lacks a value at time
  `t`, it returns `[]` orders and emits no target.

Both behaviors are intentional and reasonable. v0.4's "wait for warmup" is
arguably the more correct default — the strategy hasn't enough data to make
its trend call yet, so the catch-all branch firing is misleading.

**Allowance:** the parity test clips `compareFrom` to the first date where
v0.4 emits a non-empty target (`v4FirstWithTarget`). Days strictly before
that are excluded from both sides. We compare the regime where both engines
genuinely agree.

## Allowance 2: Calendar drift (3 dates)

**Symptom:** v0.3 history contains rows for `2020-06-19`, `2021-06-18`, and
`2021-12-31`. v0.4 does not.

**Root cause:** v0.3's calendar is fixture-derived (`tradingDaysFromBars`
collects every date present in the yfinance bars). v0.4 uses
`USEquityCalendar`, which encodes NYSE holidays algorithmically.

- **2020-06-19, 2021-06-18**: Juneteenth. Became a federal holiday in
  June 2021. NYSE first observed it on Monday 2022-06-20 (June 19, 2022 was a
  Sunday). `USEquityCalendar` treats Juneteenth as a holiday from year zero;
  yfinance correctly returned bars for 2020-06-19 (Friday — market was open)
  and 2021-06-18 (Friday — market was open; Juneteenth fell on Saturday and
  was not observed).
- **2021-12-31**: Friday. NYSE was open. NYSE rule: when New Year's Day falls
  on Saturday, the holiday is **not** observed (no Friday closure).
  `USEquityCalendar` incorrectly treats Dec 31 as the observed NYD whenever
  Jan 1 falls on Saturday.

These are real `USEquityCalendar` bugs. They are out of scope for this phase
(the calendar will be replaced or fixed in a subsequent phase that introduces
exchange-specific calendar plug-ins). Until then, the three dates are added
to a `CALENDAR_IGNORE` set and skipped on both sides.

**Allowance:** `CALENDAR_IGNORE = { '2020-06-19', '2021-06-18', '2021-12-31' }`.
Both histories drop these dates before diffing.

## Allowance 3: Fixture upper-bound clip

**Symptom:** v0.4 generates a snapshot for `2024-12-30` (Monday session per
`USEquityCalendar`). The v0.3 history's last date is `2024-12-27`.

**Root cause:** The yfinance fixture data ends at 2024-12-27. v0.4's
`USEquityCalendar` knows nothing about the fixture and continues to schedule
sessions past that date; the test's `priceAt` fallback returns the last close,
so the run does not error but produces a snapshot at stale prices.

**Allowance:** `compareTo = min(v3Last, v4Last)` (`v3Last = 2024-12-27`).
Dates after that are excluded from both sides. This is straightforward range
clipping, not a divergence in semantics.

## What the test enforces

After applying the three allowances, on the resulting (intersection) date set:

- **Date sets are identical** (`onlyInA = []`, `onlyInB = []`).
- **Per-date target weights agree to `1e-6`** (`diffs = []`).
- **Matched cell count > 0** (currently 1886).

The comparison covers ~1146 trading days from `v4FirstWithTarget`
(~2020-10-16) through 2024-12-27 — about 4.2 years of fully-warm operation.
This is the load-bearing parity guarantee for the v0.4 rollout.
